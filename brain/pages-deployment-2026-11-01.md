# Frontend consolidation, 2026-11-01

Frontend source: `web/` on main. One React application renders the homepage at `/` and the workspace at `/app/`. Navigation, branding, theme, and UI components are shared. Hash routes (`/app/#/lab`, `/app/#/huddle/demo`, `/app/#/join`) survive static hosting refreshes. Old root hashes migrate to `/app/`. Direct app paths normalize to hashes through the Pages 404 shell. Existing `/t/`, `/h/`, `/l/` share URLs forward to the API preview routes.

GitHub workflow `.github/workflows/pages.yml` builds with Node 22, runs Playwright desktop and mobile checks against the paper API, then uploads only `web/pages-dist` to Pages. Pushes to main affecting the frontend or workflow deploy automatically. PRs build and test without deploying. The old `docs/` homepage is retained in Git history/source but is no longer the deployed artifact. `npm run build:pages` builds the actual release; plain `npm run build` alone is not the Pages packaging step.

Public API origin: `https://api.protoss.trade`, Cloudflare Tunnel to the existing Mac mini service on port 8000. `VITE_API_ORIGIN` is public configuration, never a key. Fetch omits cookies and preserves explicit bearer headers. CORS allows the production frontend origins and local preview on port 4173; no wildcard origin or credentialed cookies. Native clients and existing `app.protoss.trade` API paths remain supported.

`REDIRECT_LEGACY_FRONTEND=1` in the backend environment enables a temporary, noncached 307 redirect from the old app hostname UI entrypoints to `https://protoss.trade/app/`. Query parameters and browser hash routes survive. Enable only after Pages and the API pass the public checks. Roll back by removing this flag and restarting only `com.protoss.api`; keep the fleet running. A Pages rollback is a revert of the frontend commit followed by its workflow. API DNS can remain during rollback.
